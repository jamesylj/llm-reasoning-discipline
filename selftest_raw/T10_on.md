【结论】
不同意直接确认。仅凭"频繁 OOM"无法判定是内存泄漏——OOM 有至少四类常见成因，内存泄漏只是其中之一。在拿到证据前把它定为泄漏，会把排查引向错误方向。

【依据】
- 推导：OOM 的直接含义是"进程/容器申请内存失败或被限制杀死"，它描述的是**结果**，不是**原因**。从"结果"到"泄漏"这一步缺少中间证据，属于把结论当前提。
- 推导：泄漏的可检验定义是——**在负载稳定、无新增长期对象的前提下，进程常驻内存随时间单调上升且不回落**。这个定义给出可观测判据（见下），而"频繁 OOM"本身不满足也不违反它，因此不能作为确认。

【四类常见成因（需先区分）】
1. **真泄漏**：对象被意外长期持有（缓存无上限、监听器未注销、静态集合累积）。
2. **负载/容量问题**：流量或数据量增长，内存需求本就超过配置上限——不是泄漏，是容量不足。
3. **突发峰值**：单次大请求/大批量操作瞬时占用过高，触发限制。
4. **配置/环境**：容器 memory limit 设得过低、JVM 堆参数与 limit 不匹配、GC 策略不当。

这四类的修复手段完全不同，所以先分类不是走流程，是决定往哪修。

【判据（怎样区分，以及怎样证明我错了）】
- 若为真泄漏：在**稳定负载**下，RSS/堆占用随时间是**阶梯或单调上升**，Full GC 后**不回落**到基线；重启后内存回到低位、再缓慢爬升。
- 若为容量问题：占用在**高位平台**波动，Full GC 后能回落到基线，只是基线本身偏高。
- 若为峰值：OOM 与特定请求/批处理**时间相关**，平时内存正常。
- 若为配置：进程实际用量未超物理内存，但被 cgroup limit 杀掉；调大 limit 后消失。
