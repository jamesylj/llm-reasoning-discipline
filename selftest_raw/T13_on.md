【结论】
不能沿用。早前 A/B 讨论的是 **HTTP 客户端超时与重试**，与 MySQL 连接池的 `wait_timeout` 是两个不同层面的参数，前者不能作为后者的依据。`wait_timeout` 没有"通用建议值"，它取决于你的连接池实现、连接空闲时长分布、以及 MySQL 侧 `interactive_timeout` 的配合。若必须给一个起点：**让连接池的空闲回收时间显著小于 MySQL 的 `wait_timeout`**，而不是反过来。

【依据】
- 引用：早前 A 说的是 HTTP 客户端超时 1000ms + 重试 3 次；早前 B 的结论是"超时→重试放大→延迟尖刺"。这两条都是关于**客户端到服务端的请求重试**。
- 推导：
  1. `wait_timeout` 是 MySQL 服务端参数，含义是**服务端主动关闭空闲连接前等待的秒数**（默认常见 28800s = 8h）。
  2. 连接池的空闲回收（如 HikariCP 的 `idleTimeout`、Druid 的 `minEvictableIdleTimeMillis`）是**客户端侧**参数。
  3. 二者是"服务端关连接"与"客户端回收连接"的关系，与 HTTP 重试放大没有共同的因果链。因此早前结论在此**不构成依据**（这是 R2 意义上的"引用不适用"，不是"引用被推翻"）。
