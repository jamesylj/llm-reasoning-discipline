【逐步依赖链】

1) **拓扑**：Nginx → app(4) → Redis → MySQL。
   - 作用：确定调用链顺序，后面所有"来源"候选都必须落在这条链的某一跳上。这是**引用**（你给的上下文）。

   - 但注意：排队 ≠ 计算慢。排队可能来自连接被长事务/慢查询占住，也可能来自连接数配置过小。

5) **MySQL CPU 15%**。
   - 依赖 4)：用来判断第 4 条的排队是"算不过来"还是"等不到"。

6) **Redis P99 命令耗时 0.4ms**。
   - 依赖 1)+3)：Redis 在链路上，且承担 98% 的读。
   - 推导：0.4ms 相对 2300ms 可忽略 ⇒ **Redis 本身不是延迟来源**（就命令耗时而言）。
   - 作用：**排除** Redis 作为主因。

7) **结论**：
   - 依赖 2)+4)+5)+6)：2300ms 的尾部延迟，最可能发生在**穿透到 MySQL 的那部分请求**上，且形态是**排队等待**（连接池耗尽），而非 MySQL 计算慢（CPU 15%）或 Redis 慢（0.4ms）。
