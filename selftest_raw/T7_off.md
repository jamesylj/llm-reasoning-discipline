## 二、延迟非线性增长的通用机理（推理链条）

"非线性"通常意味着系统里存在**某个资源在接近饱和时，其等待时间趋于无穷**。核心数学直觉来自排队论：在 M/M/1 类模型里，平均等待时间

$$W = \frac{\rho}{\mu(1-\rho)}$$

其中 ρ 是利用率。当 ρ→1 时，W 以 1/(1-ρ) 的形式爆炸。这就是"非线性"的根源——**不是负载本身非线性，而是等待时间对利用率是非线性的**。

由此可以展开成一条完整的排查链：

### 第 1 层：确认是不是排队效应（最普遍）

- 现象特征：延迟在低负载时几乎不变，接近某个利用率阈值后急剧上升。
- 推理：某个共享资源（CPU 核、DB 连接、线程池、锁）被串行化，请求在该资源前排队。
- 验证：看该资源的利用率是否在拐点附近接近 100%；看队列长度是否同步上升。

### 第 2 层：区分是"资源饱和"还是"协调开销"

资源饱和：CPU、内存带宽、磁盘 IOPS、网络带宽、DB 连接数打满。

协调开销（更隐蔽，也更容易造成非线性）：
- **锁竞争**：竞争加剧时，临界区外的自旋/上下文切换成本随并发数超线性增长。
- **缓存失效**：并发升高导致缓存命中率下降，回源量放大，形成正反馈。
- **惊群/重试风暴**：超时重试在高压下成倍放大实际请求量。
- **GC**：分配速率上升 → GC 频率上升 → STW 停顿 → 请求堆积 → 更多对象存活 → 更长的 GC。这是典型的正反馈非线性。

### 第 3 层：找正反馈回路

非线性往往不是单一瓶颈，而是**反馈环**：
- 延迟上升 → 客户端超时重试 → 实际负载更高 → 延迟更高。
- 线程池满 → 请求排队 → 持有连接更久 → 连接池耗尽 → 更多排队。
- 缓存过期集中 → 同时回源 → DB 打满 → 回源更慢 → 缓存填充更慢。

识别反馈环是解释"为什么是陡增而不是缓增"的关键。

### 第 4 层：区分延迟来源

把端到端延迟拆成：网络 + 排队 + 服务处理 + 下游等待 + GC/调度。分别看它们在拐点前后的变化，才能定位是哪一段在非线性增长。

### 第 5 层：确认测量本身是否失真

- 客户端超时导致只统计到"成功请求"，掩盖了长尾。
- 采样/聚合窗口在高负载下丢点。
- 协调遗漏（coordinated omission）会让压测结果系统性低估高负载延迟。
